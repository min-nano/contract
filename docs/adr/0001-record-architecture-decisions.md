# ADR 0001: アーキテクチャ決定記録を残す

- ステータス: 採用
- 日付: 2026-08-13

## 背景

本システムは法令要件に強く縛られる。建築士法は改正が予定されており、
施行政省令の内容次第で記載事項やフローが変わる可能性がある。
また、外部サービス（マネーフォワード クラウド契約のAPI提供有無など）の制約により、
「本来こうしたかったが、こうせざるを得なかった」という判断が多数発生する。

これらの判断理由が残っていないと、数年後に「なぜこんな作りなのか」が分からず、
制約が解消された後も不合理な実装が残り続ける。

## 決定

アーキテクチャ上の重要な判断は ADR として `docs/adr/NNNN-title.md` に残す。

- 番号は連番。ファイル名はケバブケース。
- 各 ADR は「背景」「決定」「理由」「検討したが採らなかった案」「結果と再検討の条件」を含める。
- **「なぜそうしなかったか」を必ず書く。** 採用理由だけでは、後から見直すときに判断材料が足りない。
- 外部の制約に起因する決定には、**その制約が解消されたら再検討する**という条件を明記する。
- 決定を覆した場合、元の ADR を削除せず「却下」に変更し、新しい ADR から参照する。

## 結果

判断の履歴が追える。法改正やAPI提供状況の変化のたびに、
影響を受ける ADR を洗い出して再検討できる。
