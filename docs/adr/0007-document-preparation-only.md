# ADR 0007: システムの責務を「書類の作成支援」に絞り、交付・承諾・受領・保管は運用で行う

- ステータス: **採用**
- 日付: 2026-08-16
- supersedes: [adr/0002](0002-esign-provider-abstraction.md), [adr/0006](0006-self-hosted-retention.md)
- 関連: [adr/0005](0005-electronic-signature-requirement.md)（結論は維持、上乗せ措置のみ見直し）,
  [adr/0008](0008-implement-as-portal-tool.md)（実装の置き場所）

## 背景

[adr/0005](0005-electronic-signature-requirement.md) で電子署名を用いないことを決め、
[adr/0006](0006-self-hosted-retention.md) で永続保管をシステムから外した。
この2つの決定によって、**システムに残っていた機能の大半が「法令が要求していないもの」になった。**

法令が事務所に課しているのは、詰めると次の3つである。

| # | 義務 | 根拠 | 性質 |
| --- | --- | --- | --- |
| 1 | **法定記載事項を満たした契約書面を作り、相互に交付する** | 法22条の3の3 | 義務・監督処分あり |
| 2 | **重要事項説明書を作って交付し、建築士が説明する** | 法24条の7 | 義務・監督処分あり |
| 3 | 報酬の算定の根拠を明らかにするための見積書を作る | 法24条の10 | **努力義務**・監督処分なし |

このうち**システムでなければできないのは「記載事項を漏らさずに書類を作る」ところだけ**である。
交付はメールの送信、承諾と受領はメールの往復、保管はファイルを置く場所の話であり、
いずれも人の操作で完結する。**それらをシステムに載せることは法令要件ではなく、
ビジネス上のリスクヘッジ**（証跡を機械的に残す、取りこぼしを検知する）である。

現行設計はそのリスクヘッジを最大限に取った結果、次を抱えていた。

- 発注者向け画面（署名付きトークン、メールアドレス照合、ワンタイムコード、承諾画面、
  ハッシュ照合ページ、レート制限）
- Cloud SQL（契約・交付記録・監査証跡）、GCS（`-workspace`、TTL、CMEK、ライフサイクル）
- Stripe（与信確保、Webhook、オーソリ期限通知）、Cloud Scheduler / Cloud Tasks
- 未保管アラート、`archived_at` の管理
- `EsignProvider` の抽象化（→ [adr/0002](0002-esign-provider-abstraction.md)）

**1名の建築士事務所が年に数十件の契約を結ぶために、この規模は釣り合っていない。**
運用しなければならないものが増えるほど、施行日（遅くとも2027年7月31日）までに
実務へ定着させるという本来の目的から遠ざかる。

## 決定

**システムの責務を次の2つに絞る。**

1. **法定記載事項を漏らさない書類の作成**（契約書・重要事項説明書・変更契約書）
2. **報酬の算定**（業務報酬基準の略算法と、事務所の単価による補正。業務報酬内訳書の作成）

**それ以外はすべて運用で行う。** システムは関与しない。

| 行為 | 担い手 | 手段 |
| --- | --- | --- |
| 電磁的方法による交付の**承諾**（令8条） | **運用** | メールの定型文。相手方の返信で承諾を得る |
| 重要事項説明書の**交付** | **運用** | PDFをメールに添付して送信 |
| 重要事項の**説明**・免許証の提示（法24条の7） | **運用** | 対面またはビデオ通話。**実施記録は重説書面そのものに欄を設ける** |
| 契約書面の**交付**（法22条の3の3） | **運用** | PDFをメールに添付して送信 |
| 相手方からの**交付**（相互交付の成立） | **運用** | 定型の返信文をもらう（→ [01-legal-requirements.md §4.4](../01-legal-requirements.md)） |
| **保管**（電子帳簿保存法） | **運用** | Google Drive の契約書フォルダ。**事務処理規程に従う** |
| **証跡** | **運用** | 送信済みメールと保存したPDF。システムはログを持たない |

### 交付をブラウザからメールに変えたことの効果

現行設計は「発注者向け画面からダウンロードさせる」＝ **規則17条の39第1項1号ロ（閲覧に供する方法）**
を前提としていた。ロを採ると**記録した旨の通知が必須**になる（同2項3号）。

メール添付での送信は **1号イ（送信して受信者のファイルに記録する方法）** に当たり、
**通知の義務が生じない**。国交省のIT重説実施マニュアルも、a) メール送信と
b) アップロードを書き分けたうえで、**通知が必要なのは b) だけ**としている
（→ [01-legal-requirements.md §4.2.4](../01-legal-requirements.md)）。

> **号の対応（イ／ロ）は Phase 0 で規則の原文と照合する。**
> 本 ADR を書いた時点では e-Gov 法令検索へ到達できず、既存の
> [01-legal-requirements.md](../01-legal-requirements.md) の記述から整理している。

### 上乗せ措置の見直し（adr/0005 §4.2.5 の⑤⑥）

[adr/0005](0005-electronic-signature-requirement.md) は、法令の最低要件に加えて
**⑤ 編集・注釈・ページ操作への権限制限**と**⑥ PDF/A-2b 出力とバイト列の固定・再生成の禁止**を
上乗せしていた。**この2つは取り下げる。**

| 措置 | 判断 | 理由 |
| --- | --- | --- |
| ② PDFで交付（出力可能性・改変への措置） | **維持** | **法令要件。** 国交省が「改変を防止する具体的措置＝PDFファイル形式とすること等」と明示している |
| ⑤ 権限制限（編集ロック） | **取り下げ** | 法令要件ではない。**印刷・テキスト抽出は許可し続けなければならない**（規則17条の39第2項1号）ため、制限をかけるほど「許可が潰れていないこと」をテストで守る負担だけが増える。さらに**再編集（→ §「PDFそのものを保存形式にする」）と正面から衝突する** |
| ⑥ PDF/A-2b と再生成の禁止 | **取り下げ** | 法令要件ではない。Google ドキュメントの書き出しは PDF/A ではないため、PDF/A-2b を採るとPDFを自前で組み立てる必要が生じ、「雛形を差し替えれば書式改訂に追従できる」という最大の利点を失う |
| ⑦ ハッシュ値の別経路での通知 | **任意に降格** | ツールは SHA-256 を表示する。メール本文に載せるかは運用の判断とし、**必須にしない**。メール添付で送る以上、本文とPDFは同じ経路であり「別経路」が成立しない |
| ⑧ 追記専用の監査証跡 | **運用へ** | DBを持たないため。送信済みメールと保存済みPDFが証跡になる |

> **⑥の取り下げは「ハッシュが一致しなくなってよい」という意味ではない。**
> 交付したPDFは**送信済みメールの添付ファイルとして事務所の手元に残る**。
> 「渡した書面はこれだ」と示す根拠はそのファイルであり、再生成の可否とは関係しない。
> 再生成を禁じる必要があったのは、GCS上のバイト列とDBのハッシュ値を一致させ続ける
> 設計だったからで、その設計自体が無くなった。

### PDFそのものを保存形式にする（DBを置かない代わり）

契約条件のスナップショットは、DBのカラムではなく**PDFの文書情報に埋め込む**。
portal の構造計算安全証明書ツールと同じ方式である（→ [adr/0008](0008-implement-as-portal-tool.md)）。

```
フォーム入力 → 雛形（Google ドキュメント）の複製に置換 → PDF書き出し
            → その入力そのものを PDF の文書情報へ埋め込む
            → Drive へ保存
```

- **保存したPDFを開き直せば入力が完全に復元される。** 変更契約は原契約のPDFを開いて作る
- マスタを参照しないので、**事務所名や建築士の登録番号を更新しても過去の契約書の再現性は壊れない**
  （現行設計が `Contract.terms` のスナップショットで守ろうとしていたものが、そのまま得られる）
- **成果物が1つだけになる。** 契約書PDFとDBレコードの二重管理と、その整合性の心配が消える

## 何が失われるか

**正直に書く。この決定はリスクを運用へ移すものであって、消すものではない。**

| 失うもの | 影響 | どう埋めるか |
| --- | --- | --- |
| 承諾・交付・受領の**機械的な証跡** | 紛争時に「いつ何を渡したか」をシステムで示せない | 送信済みメール（Google Workspace）が証跡になる。**メールを消さない運用**を規程に書く |
| 締結前の**サーバ側ガード**（承諾未取得・重説未実施で締結を止める） | 手順の飛ばしをシステムが止められない | **チェックリスト**（→ [07-operations.md](../07-operations.md)）。重説の実施記録は重説書面そのものに欄を設け、書面が埋まらなければ手順が進まない形にする |
| 保管の**取りこぼしの検知**（未保管アラート） | 保存し忘れが静かに起きうる | ツールの保存先が最初から Drive なので、**「作る」と「保存する」が同じ操作になる**。GCSからの引き渡しという中間段階が消えたため、取りこぼす場所自体が減る |
| **契約台帳**（件数・期限・金額の一覧） | 契約の全体像がファイル一覧でしか見えない | 当面は Drive のフォルダとファイル名規則（`YYYYMMDD_取引先名_金額.pdf`）で足りる。必要になったら台帳を足す（→ [ROADMAP.md](../ROADMAP.md) Phase 4） |
| 決済（Stripe） | 手付金のオンライン受領ができない | **落とす。** 請求は従来どおりマネーフォワード クラウド請求書で行う |

> **いちばん重いのは1つ目である。** 電子署名を用いず（adr/0005）、証跡もシステムに持たない
> となると、**紛争時に示せるのはメールと保存済みPDFだけ**になる。
> それで足りるかは事務所の判断であり、**従来の紙・記名押印の実務と比べて劣後しない**
> （紙でも残るのは契約書の原本だけである）という評価に基づく。
> この評価が誤っていた場合に戻る先は「証跡だけをシステムに持つ」であって、
> 発注者向け画面の復活ではない。

## 検討したが採らなかった案

### 証跡だけを残すために軽量なDBを置く

**採らない（今は）。** 契約1件あたりの証跡はメール数通であり、それを転記して保持するために
DBとその運用（バックアップ・復旧演習・アクセス制御）を抱えるのは釣り合わない。
**紛争が現実の懸念になった時点で、契約台帳とあわせて再検討する。**

### 相手方の同意をフォームで受け取る（発注者向け画面の最小版）

**採らない。** 承諾・同意・受領確認をフォームで受けると、トークン発行・有効期限・
なりすまし対策・レート制限が芋づるで必要になる。**メールの往復にはそれらが要らない**
（相手方のメールボックスと事務所のメールボックスの両方に、こちらから改変できない形で残る）。

### 契約書PDFに電子署名を付ける

**採らない。** [adr/0005](0005-electronic-signature-requirement.md) の結論を維持する。

## リスクと緩和

| リスク | 影響 | 緩和 |
| --- | --- | --- |
| **相互交付の成立を「メール本文での同意」で構成できない** | 法22条の3の3の履行が不十分になる。**監督処分の対象** | **Phase 0 の法務レビューで最初に確認する**（→ [01-legal-requirements.md §4.4](../01-legal-requirements.md)）。成立しないなら**紙で2部を交わす**運用に戻す。書面の作成はどちらでも変わらないため、**ツールの設計は影響を受けない** |
| 手順の飛ばし（承諾を取らずに交付する等） | 交付が違法状態になる | チェックリストと、**メール定型文をツールが順番に出す**こと（→ [07-operations.md](../07-operations.md)） |
| 保存し忘れ・保存先の誤り | 電帳法の保存義務違反 | 「作る」と「保存する」を同じ操作にする。保存先フォルダのルールを規程に書く |
| **事務処理規程が未整備のまま運用を始める** | 電帳法の真実性を満たす手段がゼロになる | [adr/0006](0006-self-hosted-retention.md) の指摘は**そのまま生きている**。規程はリリース前の必須項目 |
| 契約件数が増えて運用が回らなくなる | 手作業の限界 | **その時に足す。** 足す先は「証跡」「台帳」「保存の自動化」の順で、いずれも本 ADR の構造を壊さずに載せられる |

## 結果と再検討の条件

- **落とすもの**: 発注者向け画面、Stripe、Cloud SQL、Cloud Storage、Cloud Tasks / Cloud Scheduler、
  `EsignProvider` の抽象化、PDF/A-2b、編集ロック、ハッシュ照合ページ、未保管アラート
- **残すもの**: 法定記載事項の網羅（→ [05-documents.md](../05-documents.md)）、
  報酬算定（→ [06-fee-estimation.md](../06-fee-estimation.md)）、
  運用の手順と定型文（→ [07-operations.md](../07-operations.md)）
- 次の場合に再検討する
  - 法務レビューで相互交付の構成が否定された（→ 紙面運用へ。**ツールは変わらない**）
  - 紛争が現実の懸念になった（→ 証跡の保持を検討する）
  - 契約件数が年100件を超えた、または担当者が複数人になった（→ 台帳と保存の自動化を検討する）
