# ADR 0008: 社内ポータル（portal）のツールとして実装する

- ステータス: **採用**
- 日付: 2026-08-16
- supersedes: [adr/0003](0003-object-storage-gcs-over-google-drive.md)
- 関連: [adr/0007](0007-document-preparation-only.md)

## 背景

[adr/0007](0007-document-preparation-only.md) でシステムの責務を
「法定記載事項を漏らさない書類の作成」と「報酬の算定」に絞った。
その結果、必要な機能は**社内ポータル（[portal](https://github.com/min-nano/portal)）の
構造計算安全証明書 作成ツールとほぼ同じ形**になった。

| 必要なもの | portal に既にあるか |
| --- | --- |
| 社内ユーザーの認証 | **ある**（Clerk。Google ログイン＋許可ドメイン） |
| Google ドキュメントの雛形を複製して置換し、PDFへ書き出す | **ある**（`google_docs.replace_all_text` / `google_drive.export_file`） |
| 雛形とファイルを Drive から選ぶ | **ある**（Google Picker。代理アクセストークンで発行） |
| PDF を Drive へ保存（上書き／別名で保存）し、版履歴を残す | **ある**（`<portal-edit-bar>` / `<portal-save-bar>` / `<portal-save-dialogs>`） |
| PDF に入力を埋め込み、開き直して復元する | **ある**（`structural_cert.finalize_pdf` / `parse_pdf`） |
| 雛形が改訂されて置換が起きなかったことの検知 | **ある**（`missing_placeholder_warnings`） |
| フォーム定義を単一の情報源（mapping.json）から配信する | **ある**（`form_config()`） |
| 画面とサーバで同じ計算を動かす（報酬算定に効く） | **ある**（`core/` の Rust → wasm） |
| 入力漏れがある節を自動で開く折り畳みセクション | **ある**（`<portal-section>`） |
| CI / PRプレビュー / デプロイ | **ある** |

**新しく書くのは「契約書と重要事項説明書の雛形マッピング」と「報酬算定」だけになる。**

## 決定

**contract は独立したシステムを持たず、portal のツールとして実装する。**

- ツール名（仮）: **設計等業務委託契約書 作成ツール**（`contract-formatter`）
- 画面: `frontend/tools/contract-formatter/`
- API: `/api/tools/contract-formatter/**`
- 報酬算定: `core/src/fee_*.rs`（Rust → wasm。画面とサーバが同じ実装を動かす）
- 雛形: Google ドキュメント（契約書・重要事項説明書・変更契約書・業務報酬内訳書）
- 保存: Drive（portal の他のPDFツールと同じファイル操作）

**contract リポジトリは、実装を持たないドキュメントのリポジトリとして残す。**

| contract に残るもの | 理由 |
| --- | --- |
| 法令要件（条文ベース） | 条文の調査・改正の追跡は portal の関心事ではない。**改正のたびに更新する場所**として独立している価値がある |
| 契約書・重説書面の雛形マッピング仕様 | 実装（mapping.json）の根拠。**どのフィールドがどの条文に対応するか**を条文側から書く |
| 報酬算定の仕様（告示の別表・算定式） | 同上 |
| 業務フローと運用手順・規程・メール定型文 | **システムの外側**なので、portal のREADMEには置き場所がない |
| ADR | 決定の経緯 |

## なぜ独立したシステムにしないのか

### 二重に持つものが多すぎる

独立させると、Clerk の設定・Drive の domain-wide delegation・Picker の APIキー・
Cloud Run のデプロイ・CI・デザインシステムをもう一組作って**運用し続ける**ことになる。
得られるものは「リポジトリが分かれていること」だけである。

### 発注者が触らないので、社内ツールとして正しい

[adr/0007](0007-document-preparation-only.md) で発注者向け画面を落とした。
**このツールを使うのは事務所の人間だけ**であり、それは portal の他のツールと同じ性質である。
契約書という書類の重さは、**保存先フォルダの共有設定**（→ [07-operations.md](../07-operations.md)）で
担保する話であって、アプリケーションを分ける理由にはならない。

### 書類作成ツールとしての一貫性が実務で効く

事務所が1回の案件で作る書類は、契約書・重説書面・安全証明書・現況検査レポート・
計算書と横断する。**同じ場所・同じ操作（新規作成／開く／保存／別名で保存）で作れる**ほうが、
実務は迷わない。

## adr/0003 との関係 — Google Drive を採らない判断を取り下げる

[adr/0003](0003-object-storage-gcs-over-google-drive.md) は、オブジェクトストレージに
Cloud Storage を採り Google Drive を採らないと決めた。理由は2つだった。

| # | adr/0003 の理由 | 現在の状況 |
| --- | --- | --- |
| 1 | 「リンクを知っている全員」への共有が UI から1クリックでできてしまう | **残る。** 保管先フォルダの共有設定を規程で定める（→ [07-operations.md](../07-operations.md)） |
| 2 | アカウントを持たない発注者への**期限付き公開（署名付きURL）**が Drive では作れない | **消滅。** 発注者向け画面が無くなり、交付はメール添付になった。**期限付き公開そのものが不要** |

**理由2が消えたことで、Cloud Storage を採る根拠がなくなった。**
理由1は保管先の運用ルールで扱う問題であり、保存先を Drive にするかどうかとは別である
（[adr/0006](0006-self-hosted-retention.md) も、手元保管の先として Drive を認めていた）。

**本システムはオブジェクトストレージを一切持たない。** 生成したPDFはその場で
Drive へ保存するか、ブラウザへ返す。サーバ側に置き場所を作らない。

## リスクと緩和

| リスク | 影響 | 緩和 |
| --- | --- | --- |
| portal の変更が契約書ツールを壊す | 契約書が作れなくなる | portal の CI（型・Lint・テスト）で守る。**契約書ツールのテストは「法定記載事項が全て印字されること」を含める**（→ [05-documents.md](../05-documents.md)） |
| portal のツールが増えて画面がごちゃつく | 使いにくくなる | ツール一覧の並びで整理する。**この理由でシステムを分けない** |
| 雛形（Google ドキュメント）に編集権限のある人が条項を書き換える | 意図しない契約条項で締結してしまう | 雛形フォルダの編集権限を管理建築士に限る（規程）。**雛形の改訂日を契約書に印字**し、どの版で作ったかを追えるようにする |
| Drive の障害・アクセス不能 | 書類が作れない | 雛形は Google ドキュメント、保存先も Drive なので依存は避けられない。**書き出したPDFはブラウザにもダウンロードできる**ようにし、Drive 保存が失敗しても成果物は手元に残す |
| contract リポジトリのドキュメントと portal の実装がずれる | 仕様の二重管理 | **mapping.json を単一の情報源にする**（portal の既定の作法）。contract 側は「どの条文がどのキーに対応するか」だけを持ち、フォームの並びや文言は持たない |

## 結果と再検討の条件

- portal に `contract-formatter` を実装する（→ [ROADMAP.md](../ROADMAP.md)）
- contract リポジトリからは、実装を前提とした記述（モノレポ構成、TypeScript/Hono、
  Prisma、Cloud SQL、GCS）を削る（→ [CODING_STANDARDS.md](../CODING_STANDARDS.md)）
- **契約業務が事務所の外（複数事務所での利用、発注者のセルフサービス）へ広がる場合は、
  独立したシステムを再検討する。** その場合も雛形と報酬算定は共有できる形にしておく
