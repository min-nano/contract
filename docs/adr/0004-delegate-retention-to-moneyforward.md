# ADR 0004: 永続保管はマネーフォワード クラウド契約に委ね、Cloud Storage は一時領域とする

## 背景

当初は締結済契約書・合意締結証明書・受領図面を Cloud Storage に永続保管し、
`-executed` バケットにバケットロック（保持ポリシー10年）を設定して
電子帳簿保存法の保存要件に自前で対応する設計だった。

一方、マネーフォワード クラウド契約は次を備えている（一次ソースで確認済み）。

- **契約書の送信料・保管料が0円**。契約件数・保管件数による課金や上限がない
  （[料金ページ](https://biz.moneyforward.com/contract/price/)）
- **すべての電子契約に10年間の長期署名**を付与（[機能ページ](https://biz.moneyforward.com/contract/function/)）
- **電子帳簿保存法の「電子取引」に対応**。締結された電子契約にタイムスタンプが付与される
  （[MF公式サポート](https://biz.moneyforward.com/support/contract/guide/service-guide/g020.html)）
- 契約管理台帳・検索・閲覧権限・アラート通知

つまり、保存要件を満たす仕組みが**すでにサービス側にある**。
同じものを Cloud Storage 側にもう一組作ると、保管場所が二重になり、
「どちらが正なのか」「両方消さないと消えないのか」が曖昧になる。

## 決定

**永続保管はマネーフォワード クラウド契約（および見積はクラウド請求書）に委ねる。
Cloud Storage は契約書を作るための一時領域に限る。**

| データ | 正（永続保管） | 本システム |
| --- | --- | --- |
| 締結済契約書・合意締結証明書 | MFクラウド契約 | 参照IDとメタデータのみ |
| 見積書 | MFクラウド請求書 | 同上 |
| 受領図面・契約書ドラフト・重説書面 | 一時領域（GCS） | TTLで自動削除 |
| 契約条件のスナップショット・承諾記録・重説実施記録・監査証跡 | **Cloud SQL** | ここは自システムが正 |

- GCS バケットは**1つ**（`-workspace`）。**作成から90日で自動削除**するライフサイクルを設定する。
- バケットロック（保持ポリシー10年）・バージョニング・`-executed` バケットは**廃止**する。
- `Document.storage_uri` は一時的な所在であり、消えることを前提に扱う。

**ファイルは消えるが、記録は消えない。** 承諾記録・重説実施記録・契約条件のスナップショット・
監査証跡は Cloud SQL に残す。これらは法令上の履行を示す証跡であり、
MFに送るものでもファイルでもないため、委譲の対象外。

## 理由

- **保管場所を1箇所にする。** 二重管理は同期のずれと「どちらが正か」の曖昧さを生む。
  契約書でそれをやる意味はない。
- **MFのAPIに締結済PDF本体を取得するエンドポイントがない**という制約（→ [adr/0002](0002-esign-provider-abstraction.md)）が、
  この方針では**問題でなくなる**。取得して自前で保管する必要がないため。
  制約への回避策を1つ減らせる。
- 保持ポリシー・CMEK鍵管理・バックアップ・削除運用といった、
  保管に伴う運用責任を1人の事務所で背負わずに済む。
- コストが下がる（保管料0円、GCSは一時分のみ）。

## 検討したが採らなかった案

### 従来どおり Cloud Storage に永続保管する（二重保管）

MFが落ちても手元に残る、解約してもデータが残る、という利点はある。
しかし**保管場所が2つになる代償**が大きい。どちらを正とするか、
訂正・削除をどう同期するか、税務調査でどちらを出すかが常について回る。
また、締結済PDF本体を取得するAPIがないため、
**そもそも「送信したPDF」しか手元に置けず、MF側の正本とは別物**になる。
別物を2つ持つのは、1つ持つより悪い。

### 完全にMFへ委ね、Cloud Storage を使わない

契約書PDFの生成・図面の結合には作業領域が要る。
Cloud Run のローカルディスクだけで完結させるのは、
複数リクエストにまたがる編集（発注者の追加入力 → 再生成）で破綻する。
一時領域は必要。

### 受領図面だけ永続保管する

契約に至った図面は契約書PDFに結合されてMF側に残る。
失注案件の図面を残したいかは**運用の判断**であり、
それが必要なら別途「案件アーカイブ」として設計するべきで、
契約システムのストレージ方針に混ぜない。→ 下記の課題4。

## 結果と再検討の条件

この決定は**MFへの依存を強める**。次の点を Phase 0 で詰め、
運用で担保できないと判明したら本 ADR を見直す。

| # | 課題 |
| --- | --- |
| 1 | **解約・退会時のデータ取り出し。** MF公式FAQによれば、有償契約を解約しても登録データは削除されないが**無償利用状態に移行し閲覧・出力ができなくなる場合がある**。退会後はダウンロード不可（[解約FAQ](https://biz.moneyforward.com/support/plan/faq/te07.html)）。**保存義務は自事務所に残る**ため、一括エクスポート手段を事前に確認し、手順を文書化する |
| 2 | **電帳法要件が条件付き。** MFの案内は「契約書名・契約開始日・終了日・契約金額をすべて入力すると要件を満たすことが可能」。→ `PUT /contracts/{id}/fields` を必須処理に格上げし、4項目が揃わなければ `confirm` に進ませない |
| 3 | **スキャナ保存に非対応。** 紙面フォールバック分は保存要件を満たせない。紙は紙で保存するか、別サービス（クラウドBox等）を検討する |
| 4 | **重説書面と失注案件の図面。** 前者は交付義務の履行を示す証跡が必要（法24条の7）。後者はTTLで消える。どちらも保管方針を決める |

**再検討の条件**: 上記1（エクスポート手段）が確保できない場合、
または MF から他サービスへ移行する判断をした場合は、
締結済PDFを自前で保管する構成に戻すことを検討する。
その際、[adr/0002](0002-esign-provider-abstraction.md) の `fetchExecutedDocuments` が
そのまま受け皿になる（インタフェースは残してある）。
