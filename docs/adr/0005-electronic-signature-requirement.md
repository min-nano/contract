# ADR 0005: 電子署名を用いず、自前で電磁的交付の技術的担保を置く

- ステータス: **採用**（技術的担保の設計まで確定。条文解釈の最終確認のみ Phase 0-3 の法務レビューに残す）
- 日付: 2026-08-14（2026-08-16 決定）
- 関連: [01-legal-requirements.md §4](../01-legal-requirements.md),
  [04-external-services.md §1](../04-external-services.md),
  [adr/0002](0002-esign-provider-abstraction.md), [adr/0006](0006-self-hosted-retention.md)

## 背景

当初、電子契約サービス（マネーフォワード クラウド契約）の利用を前提に設計してきた。
その前提には「電磁的方法で契約書面を交付するには電子署名が要る」という**暗黙の想定**があった。

この想定を条文で検証したところ、**建築士法は電子署名を要求していない**ことが分かった。
あわせて、現在の契約（パーソナルプラン）では**クラウド契約 API v2 の全エンドポイントが 403** で、
参照系も書き込み系も利用できない（→ [04-external-services.md §1.3](../04-external-services.md)）。
他社サービスへ移す場合は年10万円超の追加コストが発生する。

**「電子署名は本当に必要か」を先に決めないと、電子契約サービスの選定もコストも決められない。**
順序が逆になっていた。

## 決定

**電子署名（および認定タイムスタンプ）を用いない。電磁的交付は本システム内で完結させる。**

法令が要求する水準と、紛争に備えた上乗せを**明確に分けて**実装する。

| | 目的 | 手当て |
| --- | --- | --- |
| **法令遵守**（監督処分の回避） | 規則17条の39・22条の2の3 の基準充足 | **PDF形式での交付**。出力可能性・通知・承諾の手続 |
| **紛争時の備え** | 「渡した書面はこれだ」と示せる | PDF/A-2b、編集ロック、ハッシュの二経路交付、追記専用の監査証跡 |

上乗せ分は**やらなくても違法ではないが、やっておくと後で効く**もので、追加コストはほぼゼロである。

## 根拠

### 1. 条文に電子署名の要求がない

適用の連鎖は 法22条の3の3第4項 → 令8条1項（令7条準用）→ **規則17条の39**。
技術基準は第2項の3点のみで、**「電子署名」の語は建築士法・施行令・施行規則のいずれにも現れない**
（e-Gov 法令検索の全文検索で0件）。

同種の規定を並べると、立法者の書き分けが明確である。

| 法令 | 改変への措置 | 本人確認・署名者の明示 |
| --- | --- | --- |
| **建築士法** 規則17条の39 | 改変が行われていないかどうかを**確認**できる措置 | **規定なし** |
| 宅地建物取引業法 規則16条の4の8 等 | 確認できる措置 | **宅地建物取引士が明示されるものであること** |
| 建設業法 規則13条の4 | 確認できる措置 | **相手方が本人であることを確認することができる措置** |

必要な場面では明文で置かれている。とくに建設業法の請負契約（設計・工事監理と最も隣接する類型）には
本人確認措置があるのに、建築士法にはない。書き漏らしではなく意図的な差と読むのが自然である。

### 2. 国土交通省が「PDF形式とすること等」で足りると明示している

**これが決め手。** [IT重説の実施マニュアル](https://www.mlit.go.jp/jutakukentiku/build/jutakukentiku_house_fr_000125.html)
（令和3年9月1日・国土交通省住宅局建築指導課、5頁）に次の記載がある。

> ・ファイルの改変を防止する措置を講じていること
> 　**改変を防止するための具体的な措置とは、ファイルの改変を行えないようファイルの種類を
> 　ＰＤＦファイル形式とすること等とします。**

これは**重説書面**（規則22条の2の3第2項2号「改変を**防止**するための措置」）についての公式解釈である。
**より強い要求である「防止」が PDF 形式で足りる以上、契約書面の「改変が行われていないかどうかを
確認することができる措置」（規則17条の39第2項2号）が、それを上回る手当てを要するとは考えにくい。**

> **この推論は推論である。** マニュアルの対象は重説書面であり、契約書面を直接扱っていない。
> ただし要求水準の高低は条文の文言から明らかであり、
> 「強い方が PDF で足りて、弱い方に電子署名が要る」という解釈は成り立たない。

### 3. 証拠力は従来の実務と比べて実質変わらない

電子署名法3条の真正成立の推定は、本人による電子署名がある場合に働く。
これを採らない以上、推定は働かず、紛争時には成立の真正を自ら立証することになる。

**この点は事務所の判断として受け入れる。** 従来の実務（紙・記名押印）と比較して
証拠力が実質的に低下するわけではない、という評価による。
代わりに、下記の上乗せ措置で「渡した書面の同一性」を示せる状態を作る。

## 技術的担保の設計

### 法令が要求する4点（これは必ず満たす）

1. **相手方の承諾**（令8条1項→令7条準用）。規則17条の40 で示す種類・内容、規則17条の41 の取得方法、
   撤回（受けない旨の申出）への対応
2. **出力することにより書面を作成できること**（規則17条の39第2項1号）
3. **改変が行われていないかどうかを確認することができる措置**（同2号）→ **PDF形式での交付**
4. **記録した旨の通知**（同3号）。閲覧に供する方法を採るため必須

### 上乗せする措置

**PDF 側**

- **PDF/A-2b で出力する。** 長期保存形式であり、「PDFファイル形式とすること」の充足も明確になる
- **編集・注釈・ページ操作に権限制限をかける**（所有者パスワード）。
  ただし **印刷とテキスト抽出は必ず許可する。**
  上記2（出力可能性）は法令要件であり、これを潰す設定にしてはならない
- 権限制限は容易に外せるため、**補助的な措置**という位置づけを明記する

**システム側**

- 確定した PDF の**バイト列をそのまま保存**し、SHA-256 を `Document.sha256` に固定する
- **確定後の再生成を禁止する**（`Document.finalized_at` で制御）。
  PDF生成は生成時刻の埋め込み・フォントのサブセット化などで**非決定的**になりうるため、
  再生成するとハッシュが一致しなくなる。**実害のある落とし穴なのでコードレベルで塞ぐ**
- **ハッシュ値を書面本体とは別経路で相手方に渡す。**
  具体的には交付通知メールの本文に記載する（上記4の通知と兼用）。
  PDFと同じ経路・同じファイルにハッシュを載せると両方を同時に差し替えられるため、
  経路を分けることに意味がある。メール本文は相手方のメールボックスに残り、こちらから改変できない
- 照合手段を案内する（`shasum -a 256` / `certutil -hashfile`）。
  自システムにも検証ページを置く（ブラウザ内で `crypto.subtle.digest` により計算し、**ファイルは送信しない**）
- 確定・交付・通知・照合を **`ContractEvent`（追記専用・DBロールレベルで UPDATE/DELETE 禁止）** に記録する

### 電子帳簿保存法への対応

保管が自前に戻るため（→ [adr/0006](0006-self-hosted-retention.md)）、電帳法対応も自前になる。
規則4条1項が定める真実性の4択のうち、**3号イと4号を採る**。

| # | 措置 | 採否 |
| --- | --- | --- |
| 1 | タイムスタンプが付された後に授受 | — |
| 2 | 授受後速やかにタイムスタンプを付す | — |
| **3イ** | **訂正・削除を行った場合に、その事実及び内容を確認できるシステム**で授受・保存 | **採用。`ContractEvent` で満たす** |
| **4** | 正当な理由がない訂正削除の防止に関する**事務処理規程**を定め、運用し、備付け | **併用。最も安価な保険** |

**電帳法上の「タイムスタンプ」は総務大臣が認定する時刻認証業務に係るものに限定される**
（規則2条6項2号ロ）。3号イ＋4号を採ることで、この有償サービスを回避できる。

検索要件（取引年月日・取引金額・取引先）は `Contract` テーブルで満たす。

## 検討したが採らなかった案

### 認定タイムスタンプを併用する

**採らない。** 検討当初は、重説書面の「改変を**防止**するための措置」がハッシュ記録では足りず、
第三者性のある措置が要ると考えていた。しかし上記の国交省マニュアルにより、
**PDF形式で足りることが公式に示されている**ため、この理由は失われた。

電帳法についても 3号イ＋4号で満たせるため、タイムスタンプを要する場面が残らない。

> ただし**将来の選択肢としては残す。** 相手方が要求した場合、
> または政省令改正で技術基準が引き上げられた場合に導入できるよう、
> `Document` にハッシュとバイト列を保持しておく（タイムスタンプの付与対象になる）。

### 電子契約サービスを利用する（現行路線の維持）

**採らない。** 証拠力は最も高いが、次の理由による。

- **現在 API が使えない。** パーソナルプランでは v2 の全エンドポイントが 403 で、
  参照系すら利用できない（→ [04-external-services.md §1.3](../04-external-services.md)）
- API を使えるようにする費用が不明。他社サービスへ移す場合は**年10万円超の追加コスト**が発生し、
  1名の事務所には重い
- **そもそも法令が要求していない**ものに、年間コストを払う判断になる

> **完全に捨てるわけではない。** 相手方が電子契約サービスの利用を求める場合に備え、
> `EsignProvider`（→ [adr/0002](0002-esign-provider-abstraction.md)）の実装差し替えで
> 対応できる状態を維持する。

### PDF に編集制限をかけず、ハッシュだけで担保する

**採らない。** 編集制限のコストはゼロに近く、外せるとはいえ「不用意な改変」は防げる。
やらない理由がない。ただし**印刷とテキスト抽出は必ず許可する**（法令要件を潰さないため）。

## 結果と再検討の条件

- **規則17条の39第2項の3基準を満たすことを、実装とテストで明示的に担保する。**
  「たぶん満たしている」では監督処分（法26条2項1号）のリスクを負う。
  基準ごとに対応するテストを書き、根拠条文をコメントに残す（→ [CODING_STANDARDS.md](../CODING_STANDARDS.md)）
- **印刷・テキスト抽出を禁止する設定を入れてはならない。** これは法令要件の充足を壊す。
  PDF生成のオプションを変更する際は、この点をレビュー項目にする
- **確定後のPDF再生成を禁止する。** ハッシュの一致が崩れる
- Phase 0-3 の法務レビューで次を確認する
  - 「署名又は記名押印」の要件が電磁的方法において不要と読めるか（本 ADR の根拠1）
  - 契約書面についても国交省マニュアルの解釈が及ぶと考えてよいか（本 ADR の根拠2の推論部分）
  - 推定効を持たない電磁的交付を消費者契約で採ることの実務上のリスク（本 ADR の根拠3）
- **改正法に伴う政省令改正**が公布された時点で本 ADR を再検証する。
  規則17条の39 は「延べ面積が三百平方メートルを超える建築物に係る契約」という見出しのままであり、
  面積要件の撤廃に合わせて改正される。その際に技術基準が変わる可能性がある
- 相手方が電子署名を求めた場合、または相手方の社内規程で電子契約サービスの利用が指定された場合は、
  `EsignProvider` の実装差し替えで対応する
