# ADR 0006: 締結済書面の永続保管を自前に戻す（ADR 0004 を supersede）

- ステータス: **採用**
- 日付: 2026-08-16
- supersedes: [adr/0004](0004-delegate-retention-to-moneyforward.md)
- 関連: [03-architecture.md §4・§6](../03-architecture.md), [adr/0003](0003-object-storage-gcs-over-google-drive.md),
  [adr/0005](0005-electronic-signature-requirement.md)

## 背景

[adr/0004](0004-delegate-retention-to-moneyforward.md) は、締結済契約書・合意締結証明書の
**永続保管をマネーフォワード クラウド契約に委ね、Cloud Storage は一時領域に限る**と決めた。
その根拠は次の4点だった。

1. 保管場所を1箇所にする（二重管理を避ける）
2. **MFのAPIに締結済PDF本体を取得するエンドポイントがない**ため、自前保管しても
   「送信したPDF」しか手元に置けず、MF側の正本とは別物になる
3. 保持ポリシー・鍵管理・バックアップ・削除運用の責任を負わずに済む
4. コストが下がる（MF側は保管料0円）

**このうち根拠2と、前提そのものが崩れた。**

- 根拠2: クラウド契約 API v2 の `GET /contracts/{id}/document` で**正本そのものを取得できる**
  （→ [04-external-services.md §1](../04-external-services.md)）。「別物を2つ持つ」という問題は生じない
- **前提**: [adr/0005](0005-electronic-signature-requirement.md) により、
  **電子署名を用いず電磁的交付を自前で完結させる**ことを決めた。
  MFクラウド契約を使わない以上、**MFに預ける対象そのものが存在しない**

つまり adr/0004 は、選択肢の比較としてではなく、**前提の消滅**により維持できない。

## 決定

**締結済契約書・重要事項説明書・合意記録の永続保管を、本システム（Cloud Storage + Cloud SQL）で行う。**

| データ | 正（永続保管） | 保管期間 |
| --- | --- | --- |
| **確定した契約書PDF**（法22条の3の3の相互交付の対象） | **Cloud Storage** | 電帳法の保存期間に従う。既定10年 |
| **重要事項説明書PDF**（法24条の7） | **Cloud Storage** | 同上 |
| 受領図面・契約書ドラフト（確定前） | Cloud Storage（一時領域） | TTL 90日で自動削除 |
| 契約条件のスナップショット・承諾記録・重説実施記録・監査証跡 | **Cloud SQL** | 削除しない（追記専用） |

### バケットを2つに分ける

adr/0004 で「1つ（`-workspace`）」にしたが、**保管要件が復活したため分離する**。
[adr/0003](0003-object-storage-gcs-over-google-drive.md)（GCS を採用する判断）は変わらない。

| バケット | 用途 | ライフサイクル | バージョニング | 保持ポリシー |
| --- | --- | --- | --- | --- |
| `-workspace` | 受領図面・生成中のドラフト。**作業領域** | **作成から90日で自動削除** | 不要 | 不要 |
| `-executed` | **確定した契約書・重説書面。永続保管** | **自動削除しない** | **有効** | **バケットロック（10年）** |

共通設定: uniform bucket-level access 有効、公開アクセス防止を組織ポリシーで強制、CMEK 適用。
発注者へのファイル配布は署名付きURL（有効期限15分）。

### 確定と同時に `-executed` へ固定する

```
ドラフト生成（-workspace）
  → 内容確定
  → PDF/A-2b で出力し、そのバイト列を -executed に格納
  → SHA-256 を計算して Document.sha256 に固定、finalized_at を立てる
  → 以後、再生成しない（→ adr/0005）
```

**確定後のオブジェクトは差し替えない。** 訂正が必要な場合は新しい版を作り、
`Contract.version` と `parent_contract_id` で履歴を残す（変更契約は法22条の3の3第2項の対象）。

## 理由

- **保管する対象が自分のところにしかない。** 電子署名を用いず自前で交付する以上、
  正本は本システムが作り、本システムが持つ。委ねる先がない
- **電帳法の保存義務は自事務所に残る。** adr/0004 の課題1（解約・退会時のロックイン）は、
  MFに委ねないことで**そもそも発生しなくなる**
- **バケットロックで保存要件を構成として強制できる。** 運用の注意力に依存しない
- adr/0004 の根拠1（保管場所を1箇所にする）は**むしろ強化される**。
  MFと自前の二重管理がなくなり、正本は Cloud Storage の1箇所になる

## 検討したが採らなかった案

### MFクラウド契約を保管専用に使い続ける

**採らない。** 契約書をMFに送るには締結フローに乗せる必要があり、
そのためのプランとAPIが使えない（→ [04-external-services.md §1.3](../04-external-services.md)）。
保管のためだけに年間コストを払う理由がない。

### 一時領域のまま運用し、必要に応じて手元へ退避する

**採らない。** 保存義務のあるデータをTTL付きの領域に置き、
消える前に人が退避する運用は事故を招く。**構成で保証する。**

### クラウドBox 等の電帳法対応ストレージを使う

**現時点では採らない。** Cloud Storage のバケットロック＋追記専用の監査証跡で
規則4条1項3号イ・4号を満たせる見込みであり、追加サービスの費用に見合わない。
ただし**紙面フォールバック分**（スキャナ保存）が必要になった場合は再検討する（下記の課題2）。

## 結果と再検討の条件

adr/0004 が挙げていた課題のうち、**1は消滅し、2〜4は残る**。

| # | 課題 | 状況 |
| --- | --- | --- |
| 1 | 解約・退会時のデータ取り出し | **消滅。** MFに預けないため |
| 2 | **紙面フォールバック分の保存** | **残る。** 相手方が電磁的方法を承諾しない場合の紙契約をどう保存するか。スキャナ保存の要件（解像度・階調・認定タイムスタンプ）を満たすのは負担が大きいため、**紙は紙で保存する**を既定とし、電子化は将来の検討事項とする |
| 3 | 電帳法要件の充足 | **自前対応に変わった。** 規則4条1項3号イ＋4号（→ [adr/0005](0005-electronic-signature-requirement.md)）。**事務処理規程の整備が必要**（Phase 0-10） |
| 4 | 重説書面と失注案件の図面 | **重説書面は `-executed` に永続保管すると決めた**（交付義務の履行を示す証跡）。失注案件の受領図面は一時領域のTTLで消える。運用で問題が出たら「案件アーカイブ」として別途設計する |

**再検討の条件**

- 保管コストが想定を超えた場合（契約書PDFは1件あたり数MB。年間数十件では問題にならない見込み）
- 相手方が電子契約サービスの利用を求めるケースが常態化した場合。
  その場合は `EsignProvider` の実装差し替えとあわせて、保管方針も見直す
- バケットロックの保持期間は**削除も短縮もできない**。設定前に保存期間を確定させること
  （建築士法に契約書の保存年限の定めはない。電帳法の7年＋αとして10年を既定とする）
