# ADR 0006: 永続保管はシステムで持たず、事務所の手元で行う（ADR 0004 を supersede）

- ステータス: **採用**
- 日付: 2026-08-16
- supersedes: [adr/0004](0004-delegate-retention-to-moneyforward.md)
- 関連: [03-architecture.md §4・§6](../03-architecture.md), [adr/0003](0003-object-storage-gcs-over-google-drive.md),
  [adr/0005](0005-electronic-signature-requirement.md)

## 背景

[adr/0004](0004-delegate-retention-to-moneyforward.md) は、締結済契約書の**永続保管を
マネーフォワード クラウド契約に委ねる**と決めた。しかし
[adr/0005](0005-electronic-signature-requirement.md) で**電子署名を用いず電磁的交付を
自前で完結させる**ことを決めたため、**預ける先そのものが存在しなくなった。**

代替として「Cloud Storage に永続保管用バケット（`-executed`）を設ける」案を検討したが、
**採らない。**

- **コストが純増する。** 金額自体は小さい（契約書PDFを年30件×5MB とすると10年累積で約1.5GB、
  GCS Standard 東京で月約5円、CMEK鍵代を含めて月10円程度）が、
  保管専用のインフラを増やす判断になる
- **事務所の既存ワークフローと合わない。** 図面のやりとりと保管には既に Google Drive を使っており
  （→ [adr/0003](0003-object-storage-gcs-over-google-drive.md)）、契約書だけ別の場所に置く必然性がない
- **手元にデータがある状態のほうが、事務所として管理しやすい**

## 決定

**本システムは締結済書面を永続保管しない。**
代わりに、**確定した書面を確実に事務所の手元へ引き渡すことに責任を持つ。**

保管先は事務所が管理する場所（Google Drive 等）とし、システムは関与しない。

### 引き渡しの設計

```
契約書PDFを確定
  ├─ -workspace の executed/ プレフィックスに格納（TTL 365日）
  ├─ SHA-256 を Document.sha256 に固定、finalized_at を立てる
  ├─ 【事務所宛】確定通知メール（PDF添付＋ハッシュ値）
  ├─ 【発注者宛】交付通知メール（ダウンロードリンク＋ハッシュ値）
  └─ 管理画面に「保管用ダウンロード」導線を出す
        ↓
     事務所が Drive 等へ保存し、画面で「保管済み」を記録（archived_at）
        ↓
     未保管のまま期限が近づいたらアラート
```

**`executed/` の TTL 365日は「保管」ではなく「引き渡しの猶予」である。**
90日（`-workspace` の既定）では短すぎて事故を招くため延ばすが、永続保管の代わりではない。
滞留量は最大でも1年分（上記の前提で約150MB、月約4円）に収まる。

### システムに残るもの

ファイルの実体は手元から消えるが、**何をどういう条件で締結し、いつ誰に渡したかは
自システムだけで説明できる**状態を保つ。

| 残すもの | 用途 |
| --- | --- |
| `Document.sha256` / `finalized_at` | **相手方が手元のPDFのハッシュを照合できる。** 実体がなくても照合は成立する |
| `Contract.terms`（法定記載事項のスナップショット） | 契約内容の再現 |
| `DocumentDelivery`（交付・通知・受領確認の記録） | 規則17条の39・22条の2の3 の充足を示す証跡 |
| `ContractEvent`（追記専用） | 監査証跡 |

> **ハッシュの照合は自システムがファイルを持っていなくても成立する。**
> 相手方は自分の手元のPDFのハッシュを計算し、通知メールに記載された値と比べればよい。
> システム側に必要なのは**記録された値**だけである。

## 電子帳簿保存法への影響（ここが最も重要）

**保存場所がシステム外に出るため、要件の満たし方が変わる。**

### 真実性の確保 — 4号（事務処理規程）が唯一の手段になる

規則4条1項の4択のうち、**3号イ（訂正削除の事実及び内容を確認できるシステムで授受及び保存を行う）は
使えなくなる。** 条文が「当該取引情報の**授受及び当該電磁的記録の保存**を行うこと」と定めており、
**保存もそのシステムで行うことを求めている**ためである。Drive 等での保存はこれに当たらない。

→ **4号「正当な理由がない訂正及び削除の防止に関する事務処理の規程を定め、
当該規程に沿った運用を行い、当該電磁的記録の保存に併せて当該規程の備付けを行うこと」に依拠する。**

> **これまで4号は「保険」として併用する位置づけだったが、**
> **唯一の真実性確保手段に格上げされた。** 規程を作っただけでは足りず、
> **運用と備付け**まで揃って要件充足になる。Phase 0-10 の優先度を上げる。

### 可視性の確保 — 小規模事業者の特例で検索要件が外れる見込み

規則4条1項の柱書は、次の場合に検索要件を**除く**と定める。

> 当該保存義務者が、その**判定期間に係る基準期間における売上高が五千万円以下である事業者である場合**
> （中略）**であって、当該電磁的記録の提示等の要求に応じることができるようにしているとき**は、
> 同号に掲げる要件（＝検索機能）を除く。

**1名の建築士事務所は該当する見込みが高い。** ダウンロードの求めに応じられるようにしておけば、
検索機能の実装は不要になる。

ただし**該当しなくなる可能性に備え、ファイル名規則を運用に入れる。**

```
YYYYMMDD_取引先名_金額.pdf     例: 20270415_山田太郎_3300000.pdf
```

これは国税庁が示す一般的な対応方法であり、規程とあわせて Phase 0-10 で定める。

## ADR 0003 との関係 — Drive を使わない判断は維持する

[adr/0003](0003-object-storage-gcs-over-google-drive.md) は Google Drive を採らないと決めた。
その理由は次の2点だった。

1. 「リンクを知っている全員」への共有が**UIから1クリックで**できてしまう
2. アカウントを持たない発注者への**期限付き公開（署名付きURL）**が Drive では作れない

**この判断は変わらない。** 本 ADR が Drive を保管先として認めるのは、
**事務所の手元保管**についてのみである。区別を明確にする。

| 用途 | 保管先 | 根拠 |
| --- | --- | --- |
| **発注者への配布** | **Cloud Storage の署名付きURL（15分）** | Drive では期限付き公開ができない（adr/0003 理由2） |
| **システムが扱う作業領域** | **Cloud Storage `-workspace`** | 同上 |
| **事務所の手元保管**（本 ADR） | **Drive 等。事務所が管理する** | 配布経路ではないため adr/0003 の理由が当たらない |

> **理由1（誤共有のリスク）は手元保管でも残る。**
> 契約書と図面には個人情報が含まれるため、**保管先フォルダの共有設定を運用ルールで定める**こと。
> Phase 0-7（個人情報取扱規程）に含める。

## 検討したが採らなかった案

### Cloud Storage に永続保管用バケットを設ける

**採らない。** コストが純増し、事務所の既存ワークフローと合わない（→ 背景）。

> **ただし、この案には失われる利点がある。** バケットロックによって
> **保存義務の履行を構成で強制できた。** 手元保管ではこれが**運用依存**になる。
> 下記のリスクと緩和策で埋める。

### `-workspace` の TTL を10年にする

**採らない。** それは実質的に永続保管用バケットを作るのと同じで、コストも同じだけかかる。
作業領域と保管領域の区別が曖昧になり、失注案件の図面まで10年残ることになる。

### 確定PDFをメール添付だけで渡し、GCSに置かない

**採らない。** メールは添付サイズの上限があり（受領図面を結合すると数十MBになりうる）、
送達の失敗が起きうる。**ダウンロード経路は必ず残す。**
メールは「気づかせる」手段であって、唯一の引き渡し経路にはしない。

## リスクと緩和

| リスク | 影響 | 緩和 |
| --- | --- | --- |
| **ダウンロードし忘れて TTL で消える** | **保存義務違反。取り返せない** | ① 確定と同時に事務所宛メールへPDFを添付 ② 管理画面に**未保管一覧**を常設 ③ 期限が近づいたらアラート（Cloud Scheduler） ④ `archived_at` を記録し、未記録のものを可視化 |
| Drive 側で誤って削除される | 同上 | Drive のゴミ箱・版管理に依存する。**保管先の運用ルールを規程に明記**（Phase 0-10） |
| 保管先フォルダの誤共有 | 個人情報の漏えい | 共有設定のルールを Phase 0-7 の規程に含める |
| 事務処理規程が未整備のまま運用開始 | **真実性の要件を満たす手段がゼロになる** | Phase 0-10 を**リリース前の必須項目**とする。3号イという代替がなくなったため、後回しにできない |

## 結果と再検討の条件

- **Phase 0-10（事務処理規程の整備）はリリースのブロッカーである。**
  これまでは「保険」だったが、唯一の真実性確保手段になった
- **未保管アラートの実装は Phase 1 に含める。** 運用依存のリスクを埋める中核なので、後回しにしない
- 保管の失敗（消失）が実際に起きた場合、または事務所の規模が拡大して検索要件の特例から
  外れる場合は、**永続保管用バケットの再導入を検討する**。
  その際は本 ADR を supersede する新しい ADR を起票する
- `executed/` の TTL 365日は、運用実績を見て調整する。
  短縮するときは未保管アラートが機能していることを確認してから行う
