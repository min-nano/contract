# ADR 0002: 電子契約プロバイダを抽象化する

- ステータス: 採用
- 日付: 2026-08-13（2026-08-13 改訂: クラウド契約 API v1 の発見を反映）
- 関連: [04-external-services.md](../04-external-services.md), [ROADMAP.md](../ROADMAP.md) Phase 0

## 背景

電子契約はマネーフォワード クラウド契約を利用する前提で計画している。
請求・会計をマネーフォワードで統一しており、運用上の一貫性という利点がある。

**クラウド契約 API v1 は存在する**
（<https://api.contract.moneyforward.com/v1/docs/index.html>、Swagger 2.0、認証は `x-email` + `x-token`）。
下書き作成・PDFアップロード・相手方登録・送信・リマインド・取下げ・合意締結証明書のダウンロードが揃っており、
締結フローは自動化できる。→ [04-external-services.md §1](../04-external-services.md)

ただし、このAPIには次の性質がある。

1. **開発者サイトの API リファレンスに掲載されていない。**
   製品ドキュメントから辿れない位置にあり、変更ポリシー・サポート範囲・提供条件が不明。
2. **Webhook がなく、締結状況を取得するエンドポイントもない。**
   `presenter.Contract` に status フィールドがなく、契約の取得系は下書きステータス専用と明記されている。
   締結完了の検知は「合意締結証明書の取得が成功するか」という間接的な手段に頼らざるを得ない。
3. **締結済PDF本体をダウンロードするエンドポイントがない。**
4. 署名画面はマネーフォワードのドメインで提供され、
   **UIの差し込みも遷移先の制御もできない**（APIにもリダイレクト指定のパラメータはない）。

つまり「APIはあるが、締結完了の検知まわりは今後変わる可能性が高く、
現時点の実装は回避策を含む」という状態である。
この回避策をドメイン層に直接書き込むと、API が改善されたとき、
あるいは他社サービスへ切り替える必要が生じたときに広範囲の書き直しが発生する。

## 決定

電子契約の連携を `EsignProvider` インタフェースの背後に隔離する。
ドメイン層とユースケース層は、このインタフェースだけを知る。

```ts
export interface EsignProvider {
  readonly kind: 'moneyforward' | 'manual' | ...

  /** 締結依頼を作成する（相手方への署名依頼メール送信を含む） */
  createSignatureRequest(input: SignatureRequestInput): Promise<SignatureRequestResult>

  /** 締結状況を取得する */
  getStatus(esignDocumentId: string): Promise<EsignStatus>

  /** 締結済PDF・合意締結証明書を取得する */
  fetchExecutedDocuments(esignDocumentId: string): Promise<ExecutedDocuments>

  /** 締結依頼を取り消す */
  cancel(esignDocumentId: string, reason: string): Promise<void>
}
```

実装は3種類を想定する。

| 実装 | 内容 |
| --- | --- |
| `MoneyForwardApiProvider` | **既定の実装。** クラウド契約 API v1 を呼ぶ。`getStatus` は合意締結証明書の取得可否で判定する（この回避策をこのクラスの中に閉じ込める） |
| `ManualMoneyForwardProvider` | API の利用条件が満たせない場合のフォールバック。事務所側にタスクを起票し、必要なPDF一式・宛先を揃える。締結状況はスタッフの手動記録で確定する |
| `FakeEsignProvider` | テスト・開発用 |

上位のフロー（承諾 → 重説 → 内容確認 → 決済 → 署名依頼 → 締結）は**どの実装でも変わらない**。
`ManualMoneyForwardProvider` でも、発注者から見た体験は同じである
（自サイトで「署名を依頼する」を押し、しばらくしてマネーフォワードからメールが届く）。
違いは事務所側に手作業が発生するかどうかだけ。

## 理由

- **締結完了の検知が回避策である**という事実を、1つのクラスの中に閉じ込められる。
  Webhook やステータス取得APIが提供されたとき、変更範囲がそこだけで済む。
- API の提供条件（プラン・トークン発行方法）が判明するまで、
  フロー・画面・データモデルの実装を止めずに進められる。
- ドキュメント化されていないAPIに依存するリスクへの保険になる。
  他社サービス（クラウドサイン、freeeサイン等、公開APIとWebhookを持つ）への切替が、
  最終手段として現実的な選択肢として残る。
- フォールバックの手作業運用を「暫定的な回避策」ではなく**正規の実装のひとつ**として扱うことで、
  中途半端な手作業が場当たり的にコードへ混入することを防ぐ。

## 検討したが採らなかった案

### マネーフォワードのAPIを直接呼ぶ（抽象化しない）

API があると分かった以上、これが最も素直ではある。採らない理由は2つ。

第一に、締結完了の検知が「合意締結証明書の取得を試みる」という回避策であること。
抽象化しないと、この回避策がユースケース層に漏れ、
Webhook が提供されたときに呼び出し側すべてを直すことになる。

第二に、このAPIが開発者サイトに掲載されておらず、変更ポリシーが不明であること。
仕様が変わったとき、影響範囲が1クラスに収まっている状態を維持したい。

### スクレイピング・ブラウザ自動操作でマネーフォワードの画面を操作する

**採用しない。** 利用規約に抵触する恐れがあり、画面変更で無言で壊れる。
契約締結という失敗が許されない処理を、壊れることが前提の手段に載せるべきではない。

### Webhook を持つ他社サービス（クラウドサイン、freeeサイン等）を採用する

締結完了の検知は素直になるが、請求・会計をマネーフォワードで統一している運用上の利点を失う。
ポーリングで実用上困らない見込み（署名は数分〜数日単位で、秒単位の即時性は不要）なので、
Webhook がないことだけを理由に切り替えるのは割に合わない。抽象化しておけば後から選べる。

### 署名完了後の遷移先URLを指定できる前提で、署名画面から自サイトの決済へ戻す

**APIにリダイレクト指定のパラメータは存在しない。** 実現できない。
決済は署名依頼より前に自サイトで完結させる設計にすることで、この制約から独立する。

### スクレイピングで締結状況を取得する

**採用しない。** 利用規約に抵触する恐れがあり、画面変更で無言で壊れる。
合意締結証明書の取得可否による判定のほうが、公式APIの範囲内で完結する分だけ健全。

## 結果と再検討の条件

- Phase 0 で API の利用条件（必要プラン、`x-token` の発行方法）を確認し、
  サンドボックスで一連のフローを検証したうえで `MoneyForwardApiProvider` を実装する。
- **Webhook または締結状況取得APIが提供されたら、`getStatus` の実装を差し替える。**
  このとき変更が `MoneyForwardApiProvider` の内部に収まっていることを確認する。
  収まっていなければ、この ADR の目的が達成できていないということ。
- 締結済PDF本体を取得するエンドポイントが追加されたら、`fetchExecutedDocuments` を更新する。
- API の提供条件が満たせない、または仕様変更で頻繁に壊れる場合、
  他社サービスへの切替を新しい ADR として起票する。
