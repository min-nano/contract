# ADR 0002: 電子契約プロバイダを抽象化する

- ステータス: 採用（Phase 0-1 の回答により具体実装を確定）
- 日付: 2026-08-13
- 関連: [04-external-services.md](../04-external-services.md), [ROADMAP.md](../ROADMAP.md) Phase 0

## 背景

電子契約はマネーフォワード クラウド契約を利用する前提で計画している。
請求・会計をマネーフォワードで統一しており、運用上の一貫性という利点がある。

しかし調査の結果、**マネーフォワードが一般開発者向けに公開・ドキュメント化している製品APIは
クラウド請求書APIとクラウド経費APIの2つのみ**で、クラウド契約の公開APIドキュメントは確認できなかった。
Salesforce向けアプリや iPaaS のコネクタが存在するため何らかのAPIはあると推測されるが、
利用条件・仕様は不明である。

さらに、署名画面はマネーフォワードのドメインで提供されるため、
**署名画面に決済UIを差し込むことも、遷移先を制御することもできない**。

この状態でマネーフォワードのAPIを直接呼ぶコードをドメイン層に散らすと、
API が使えないと判明した時点、あるいは他社サービスへ切り替える必要が生じた時点で、
広範囲の書き直しが発生する。

## 決定

電子契約の連携を `EsignProvider` インタフェースの背後に隔離する。
ドメイン層とユースケース層は、このインタフェースだけを知る。

```ts
export interface EsignProvider {
  readonly kind: 'moneyforward' | 'manual' | ...

  /** 締結依頼を作成する（相手方への署名依頼メール送信を含む） */
  createSignatureRequest(input: SignatureRequestInput): Promise<SignatureRequestResult>

  /** 締結状況を取得する */
  getStatus(esignDocumentId: string): Promise<EsignStatus>

  /** 締結済PDF・合意締結証明書を取得する */
  fetchExecutedDocuments(esignDocumentId: string): Promise<ExecutedDocuments>

  /** 締結依頼を取り消す */
  cancel(esignDocumentId: string, reason: string): Promise<void>
}
```

実装は3種類を想定する。

| 実装 | 内容 |
| --- | --- |
| `ManualMoneyForwardProvider` | **APIが使えない場合の既定。** `createSignatureRequest` は事務所側にタスクを起票し、必要なPDF一式・宛先・件名を揃える。締結状況はスタッフの手動記録、または締結完了通知メールのパース結果を候補として提示して確定する |
| `MoneyForwardApiProvider` | APIが利用可能と判明した場合の本命実装 |
| `FakeEsignProvider` | テスト・開発用 |

上位のフロー（承諾 → 重説 → 内容確認 → 決済 → 署名依頼 → 締結）は**どの実装でも変わらない**。
`ManualMoneyForwardProvider` でも、発注者から見た体験は同じである
（自サイトで「署名を依頼する」を押し、しばらくしてマネーフォワードからメールが届く）。
違いは事務所側に手作業が発生するかどうかだけ。

## 理由

- Phase 0-1 の回答を待たずに、フロー・画面・データモデルの実装を進められる。
- APIが後から使えるようになった場合、`EsignProvider` の実装を差し替えるだけで済む。
- 他社サービス（クラウドサイン、freeeサイン等、公開APIとWebhookを持つ）への切替が、
  最終手段として現実的な選択肢になる。
- 半自動運用を「暫定的な回避策」ではなく**正規の実装のひとつ**として扱うことで、
  中途半端な手作業が場当たり的にコードへ混入することを防ぐ。

## 検討したが採らなかった案

### マネーフォワードのAPIを直接呼ぶ（抽象化しない）

APIの提供有無が確定していない段階では書けない。
仮に書き始めても、提供されないと判明した時点で捨てることになる。

### スクレイピング・ブラウザ自動操作でマネーフォワードの画面を操作する

**採用しない。** 利用規約に抵触する恐れがあり、画面変更で無言で壊れる。
契約締結という失敗が許されない処理を、壊れることが前提の手段に載せるべきではない。

### 最初から公開APIを持つ他社サービスを採用する

技術的には最も素直だが、請求・会計をマネーフォワードで統一している運用上の利点を失う。
Phase 0-1 の回答を得る前に決める理由がない。抽象化しておけば後から選べる。

### 署名完了後の遷移先URLを指定できる前提で、署名画面から自サイトの決済へ戻す

指定可否が未確認。**指定できることを前提に設計してはならない。**
決済は署名依頼より前に自サイトで完結させる設計にすることで、この不確実性から独立する。

## 結果と再検討の条件

- Phase 0-1 で API 提供が確認できたら、`MoneyForwardApiProvider` を実装し既定を切り替える。
  このとき本 ADR は「採用」のまま、実装状況を追記する。
- Webhook が提供される場合、締結完了の検知をポーリングから Webhook に変更する。
- API が提供されず、かつ半自動運用の手間が許容できないと判明した場合、
  他社サービスへの切替を新しい ADR として起票する。
