# ロードマップ

## 制約となる日程

**建築士法の一部を改正する法律（令和8年法律第74号）／令和8年（2026年）7月31日公布。**
（一次ソース: [国土交通省](https://www.mlit.go.jp/jutakukentiku/build/jutakukentiku_house_fr_000260.html)）

| 日付 | 事象 |
| --- | --- |
| 2026-07-31 | 改正建築士法 **公布**（令和8年法律第74号） |
| **2027-07-31 まで** | **契約の適正化（法22条の3の3・22条の3の4・24条の10・26条2項1号）の施行期限**。実際の施行日は政令で定まる |
| 2029-07-31 まで | 将来の建築士等の確保（受験資格の緩和、建築設備士の登録制度）の施行期限。本システムには軽微 |

施行日は政令待ちだが、**上限は2027年7月31日**。運用の定着には数か月かかるため、
**2027年1月に本番稼働、2027年4月までに全契約種別を移行**を目標とする。
施行期日政令が公布されたら本ロードマップを見直す。

**経過措置**: 改正法附則第4条により、新法22条の3の3は**施行日以後に締結される契約**に適用される
（施行日前の契約は従前の例による）。施行日をまたぐ案件があるため、
契約レコードは締結日と適用法令バージョンを保持する。

## Phase 0 — 前提の確定（2026-08 〜 2026-09）

**コードを書く前に、設計を左右する不確実性を潰す。**

> **2026-08-16: 方針が大きく変わった。**
>
> 当初は電子契約サービス（マネーフォワード クラウド契約）の利用を前提としていたが、
> **建築士法は電磁的方法による契約書面の提供に電子署名を要求していない**ことが条文で確認され、
> さらに国交省が「改変を防止する措置＝**PDFファイル形式とすること等**」と明示していることが分かった。
> → [01-legal-requirements.md §4.2](01-legal-requirements.md)
>
> **電子署名を用いず、電磁的交付を本システム内で完結させる**ことに決定した
> （→ [adr/0005](adr/0005-electronic-signature-requirement.md)）。これに伴い:
>
> - **外部の電子契約サービスへの依存がなくなった。** クラウド契約 API の403問題（→ 04 §1.3）も、
>   他社サービスへの乗り換え検討も、**本線から外れた**
> - **保管は事務所の手元で行う**（→ [adr/0006](adr/0006-self-hosted-retention.md)）。
>   システムは永続保管せず、確定書面を確実に引き渡すことに責任を持つ。
>   電帳法の真実性は**規則4条1項4号（事務処理規程）が唯一の手段**になる
> - **Phase 0 の外部依存がほぼ消え、実装に着手できる状態になった**

**Phase 0 のゲート**

- **0-3 の結論が出るまで、契約書・重説書面を実際に発注者へ交付しない。**
  条文解釈の最終確認が済むまでは、開発・検証環境の範囲にとどめる
- **0-11 の検証が済むまで、PDF生成の実装方針を固定しない。**
  「印刷・テキスト抽出を許可したまま編集を制限する」が実現できることが前提条件になる
  （できなければ法令要件を満たせない。→ [01-legal-requirements.md §4.2.5](01-legal-requirements.md)）

**外部サービスの回答待ちが Phase 0 のクリティカルパスから外れた。**
0-4 以降と Phase 1 は並行して着手できる。
`EsignProvider` は `SelfHostedProvider` が既定の実装になる（→ [adr/0002](adr/0002-esign-provider-abstraction.md)）。

## Phase 1 — MVP: 設計受託契約の電子契約（2026-10 〜 2026-12）

**目標**: 新築設計案件1件を、見積送付から締結まで本システムで完結させる。

### スコープ

- 案件（`Project`）・発注者（`Client`）管理、受領資料のアップロードとハッシュ固定
- 見積書PDFの登録（作成はMFの画面。API化は Phase 4）と、契約用リンク入りメールの送信
- 発注者向け画面
  - トークン認証（メールアドレス照合）
  - **① 電磁的方法による交付の承諾**（種類・内容の表示、承諾記録、撤回導線）
  - **② 重要事項説明書の閲覧・ダウンロード**
  - **④ 契約内容の確認・追加入力**（受領図面を別紙目録付きで添付）
  - **⑥ 契約書の受領・内容確認**（ワンタイムコードによるステップアップ認証）
  - **ハッシュ値の照合ページ**（ブラウザ内で計算。ファイルは送信しない）
- 事務所向け管理画面
  - **③ 重要事項説明の実施記録**の登録（説明者・資格・登録番号・方法・免許証提示）。
    **IT重説の場合は国交省マニュアルの遵守6項目**（→ [01-legal-requirements.md §3.3](01-legal-requirements.md)）
    ※ 相手方が建築主の場合のみ。元請け設計事務所からの受託では重説は不要（法24条の7）
  - 契約書ドラフトの作成・差戻し対応
  - 交付状況・受領確認状況の確認
- **電磁的交付の自前実装**（`SelfHostedProvider`。→ [adr/0005](adr/0005-electronic-signature-requirement.md)）
  - **契約書PDF生成**（法定記載事項を全網羅、**PDF/A-2b**、双方の記名を印字）
  - **受領図面は契約書PDFに結合して1つのPDFにする**（交付対象に図面を含める）
  - **確定処理**: バイト列を `executed/` に格納 → SHA-256 を固定 → `finalized_at` → **再生成禁止**。
    ファイル名は `YYYYMMDD_取引先名_金額.pdf`（電帳法の検索要件への備え）
  - **編集ロック**（印刷・テキスト抽出は許可。**法令要件なので潰さない**）
  - **交付と通知**（通知メールにハッシュ値を記載。書面本体とは別経路）
  - **受領確認**と、相互交付の成立判定（承諾＋交付通知＋受領確認）
  - リマインド、取下げ
- **GCS 1バケット構成**（`-workspace`。既定TTL90日／`executed/` は365日）
- **手元保管への引き渡し**（→ [adr/0006](adr/0006-self-hosted-retention.md)）
  - 確定と同時に**事務所宛へPDF添付メール**、管理画面に**保管用ダウンロード**導線
  - `archived_at` の記録と、**未保管一覧＋期限アラート**（Cloud Scheduler で日次）
  - **消えたら取り返せないため、後回しにしない**
- 監査証跡（`contract_events`、追記専用・**DBロールレベルで UPDATE/DELETE 禁止**）。
  電帳法の要件充足の根拠にはならないが（→ [03-architecture.md §6](03-architecture.md)）、
  **電子署名を用いない以上、紛争時の裏付けはここしかない**
- 状態遷移のサーバ側ガード（承諾未取得、および**重説の適用がある契約で**重説未実施の場合は締結に進めない）
- 相手方が建築主か（`Client.is_building_owner`）による重説要否の判定

### スコープ外（意図的に落とす）

- 決済（Phase 2）
- 設計以外の契約種別（Phase 3）
- 変更契約（Phase 3）※ただしデータモデルは Phase 1 で対応しておく
- 見積作成のAPI化と業務報酬内訳書（Phase 4）
- ワークフロー承認、契約台帳の分析機能

### 完了条件

- 実案件1件を本システムで締結できた
- 法定記載事項の検証テストが `packages/domain` に揃っている
- E2E（リンクを開く → 締結）が1本通る

## Phase 2 — 決済と消費者対応（2027-01 〜 2027-02）

**目標**: 一般消費者の発注者から手付金・前払金を受け取れる。本番稼働。

- Stripe PaymentIntent（manual capture）の実装
  - 締結不成立時の cancel、締結完了時の capture
  - オーソリ期限（約7日）が近い案件の通知（Cloud Scheduler）
  - Webhook の署名検証と冪等処理
- 決済ステップを契約フローに組み込む（決済 → 契約書の確定・交付の順）
- 消費者向けの表示整備
  - 特定商取引法に基づく表記
  - 決済前の最終確認画面（金額・支払時期・返金条件）
  - 消費者契約法を踏まえた解除・違約金条項の見直し（Phase 0-3 の法務レビュー反映）
- 契約種別ごとの決済要否・方式（与信 or 即時）の設定
- **本番稼働**（施行の半年前）

## Phase 3 — 汎用化と変更契約（2027-03 〜 2027-04）

**目標**: 設計以外の業務と、実務で必ず起きる契約変更に対応する。

- **契約種別の一般化**（`ContractType` の実装）
  - 工事監理受託契約（法22条の3の3第1項2号の記載事項に対応）
  - 建築物調査・検査（定期報告等）
  - 耐震診断
  - その他コンサルティング
  - 種別ごとに「書面相互交付の要否」「重説の適用候補」「見積書の推奨」「適用する業務報酬基準の告示」
    「テンプレート」「入力スキーマ」を切替（義務ごとに対象範囲が異なる → [01-legal-requirements.md §5](01-legal-requirements.md)）
  - **重説の要否は種別マスタだけでは決まらない**。相手方が建築主かと組み合わせて判定する
- **耐震診断**（見積書の努力義務の対象。書面相互交付・重説は対象外。報酬は告示第670号）
- **変更契約**（法22条の3の3第2項）
  - 契約のバージョン管理、親契約への参照、変更点の差分表示
  - 変更書面の相互交付フロー（承諾は原契約時のものを流用、重説は不要）
- 設計・工事監理の一括契約（1件で両方を受託するケース）
- **元請け設計事務所からの受託**（相手方が建築主でないケース。重説不要・書面相互交付は必要）
- **再委託の登録**（法24条の3。相手が建築士事務所の開設者であることの必須化、
  300㎡超の新築工事における一括再委託の確認。規則17条の38第6号の記載と連動）
- **改正法の施行政省令を反映**（記載事項の変更があれば `docs/01-legal-requirements.md` を改訂し、
  スキーマとテンプレートに反映）
- 全案件を本システムに移行（面積によらず書面契約）

## Phase 4 — 見積のAPI化と請求連携（2027-05 〜 2027-07）

**目標**: 見積作成から請求までを本システムで完結させ、報酬の根拠を示せる見積書を標準運用にする。

> **位置付け**: 法24条の10（新設）は**努力義務**であり、監督処分の対象にも含まれない
> （法26条2項1号の列挙外）。書面契約義務のような期限のある強制ではない
> （→ [01-legal-requirements.md §1.5](01-legal-requirements.md)）。
> したがって Phase 4 は**施行日に間に合わせる必要がない**。
> Phase 1〜3（書面契約義務への対応）を優先し、遅延した場合は本フェーズを後ろにずらす。
> 一方で報酬の根拠を示せることは実務上の価値が高いため、スコープからは落とさない。

- MFクラウド請求書 API v3 連携（OAuth 2.0、トークンのリフレッシュ管理）
  - `POST /quotes` で見積作成、`pdf_url` を取得
  - `/partners` と `Client` の同期
  - `PUT /quotes/{id}/order_status` で受注ステータスを契約締結と連動
  - `POST /quotes/{id}/convert_to_billing` で締結後に請求書を生成
- **業務報酬内訳書**の生成（令和6年告示第8号の略算法に基づく算定根拠）
  → 法24条の10（努力義務）への対応。**見積未作成でも契約フローは進行できるようにする**（警告は出す）。
  告示第8号・告示第670号で費目構成が異なるため、算定器は告示別に実装する
- 見積書PDFへの契約用リンク自動埋め込み（PDF生成の内製化）
- 見積 → 契約 → 請求のステータス一気通貫

## Phase 5 — 契約管理・運用改善（2027-08 〜）

- 契約台帳（**メタデータの検索**。ファイル実体は事務所の手元にあるため、
  検索結果から保管先を特定できることを目標にする。
  電帳法の検索要件は小規模事業者の特例で外れる見込みだが、
  該当しなくなった場合に備えて取引年月日・取引金額・取引先の複合検索を用意する）
- 契約期限・更新・工期のアラート
- 過去の紙契約の取り込み（スキャナ保存の要件は負担が大きいため、
  **紙は紙で保存する**を既定とする。→ Phase 0-10）
- 事務所内の承認ワークフロー
- 多者間契約（施主・施工者・設計事務所の三者契約など）
- ダッシュボード（受注率、見積〜締結のリードタイム、契約種別別の実績）

## リスクと対応

| リスク | 影響 | 対応 |
| --- | --- | --- |
| **電子署名を用いない判断が法務レビューで覆る** | 電子契約サービスの導入が必要になり、年間コストとスケジュールに影響する | Phase 0-3 を早期に実施する。`EsignProvider` の抽象化により、覆っても**上位フローは変わらない**（→ [adr/0002](adr/0002-esign-provider-abstraction.md)）。実装のやり直しは `SelfHostedProvider` の範囲に収まる |
| **PDF の権限制限が出力可能性を潰す** | **法令要件（規則17条の39第2項1号）を満たさなくなる**。監督処分のリスク | 印刷・テキスト抽出の許可を**テストで固定する**。Phase 0-11 で生成方式を検証してから実装方針を決める |
| **確定PDFの再生成でハッシュが一致しなくなる** | 「渡した書面はこれだ」と示せなくなる | 確定後の再生成を `Document.finalized_at` でコードレベルに封じる。バイト列をそのまま保存する（→ [adr/0005](adr/0005-electronic-signature-requirement.md)） |
| 相手方が電子契約サービスの利用を求める | 自前実装では対応できないケースが出る | `EsignProvider` の実装差し替えで対応する。クラウド契約 API v2 の調査結果は記録済み（→ [04-external-services.md §1](04-external-services.md)） |
| 受領図面を別ファイルとして添付できない | 契約書と図面が分離する | 図面を契約書PDFに結合する方針を既定とする。署名対象に含まれるため要件にはむしろ適合 |
| 施行期日政令が想定より早い日を指定する | 移行が間に合わない | Phase 1 のスコープを「設計受託契約のみ」に絞ってある。最悪 Phase 3 の汎用化を後回しにし、設計契約だけ先に義務対応する |
| 重説の要否を契約種別だけで判定してしまう | 元請け受託で不要な重説を強制し、締結を止めてしまう | 要否は「契約種別 × 相手方が建築主か」の判定関数で導く。テストで両ケースを固定する |
| 施行に伴う政省令改正で記載事項が変わる | スキーマ・テンプレートの改修 | 法定記載事項を `packages/domain` に集約し、1箇所の変更で済む構造にする |
| 改正で法22条の3の3の**項番号が繰り上がる**（電磁的方法: 4項→3項、24条の8不適用: 5項→4項） | コード中の条文参照コメントが古くなる | 施行時に一括で見直す。条文参照は `packages/domain` に集約しておく |
| IT重説が認められない | 対面説明が必須になり、オンライン完結が崩れる | Phase 0-3 で確認。認められない場合、重説は対面で実施し、システムは書面交付と実施記録のみを担う（フロー自体は成立する） |
| 発注者が電子署名を拒否する | 締結できない | 紙面交付フォールバックを Phase 1 から実装する（法24条の8書面の経路） |
