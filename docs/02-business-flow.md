# 業務フロー

## 1. 全体フロー

```
[事務所]                          [発注者]                       [外部サービス]

図面等の資料を受領 ──────────────── 見積依頼
   │
   ├─ 案件(Project)登録・受領資料アップロード
   │
見積作成（当面はMFクラウド請求書の画面、将来はAPI）
   │
見積書PDF＋契約用リンクをメール送付 ──→ メール受信
   │                                      │
   │                                  リンクを開く（トークン認証）
   │                                      │
   │                                  ① 電磁的方法による交付の承諾
   │                                      │
   │                                  ② 重要事項説明書の閲覧
   │                                      │  ※ 相手方が建築主の場合のみ（法24条の7）
   ├─ ③ 重要事項説明の実施（対面/ビデオ通話・免許証提示）
   │      説明実施記録を登録            │  ※ 同上。元請け受託時はスキップ
   │                                      │
   │                                  ④ 契約内容の確認・追加入力
   │                                      │  （受領図面等を添付した契約書を提示）
   │                                      │
   │                                  ⑤ 決済（消費者向け：手付金/前払）─→ Stripe
   │                                      │
   │                                  ⑥ 「署名を依頼する」ボタン
   │                                      │
   ├─ 締結依頼を送信 ─────────────────────────────────→ MFクラウド契約
   │                                      │                     │
   │                                  署名依頼メール受信 ←──────┘
   │                                      │
   │                                  MFの画面で電子署名
   │                                      │
   ├─ 事務所側で署名（相互交付の成立） ←──┘
   │
締結完了 ─────────────────────→ 締結済PDF・合意締結証明書を通知
   │
   ├─ 締結済契約書はMF側に保管（自システムは参照IDとメタデータのみ）
   ├─ 決済を確定（オーソリのキャプチャ）
   └─ 一時領域の作業ファイルはTTLで自動削除
```

## 2. 各ステップの詳細と要件

### 2.0 案件登録・資料受領（事務所）

- 発注者（`Client`）と案件（`Project`）を登録する。
- 受領した図面・資料をアップロードする。ファイルは**受領時のハッシュ値を記録**し、
  契約書添付時に同一性を証明できるようにする。
- **アップロード先は一時領域**（作成から90日で自動削除）。契約に至った図面は契約書PDFに結合され、
  MF側に永続保管される。**ハッシュとファイル名の記録は実体が消えた後も残す**
  （→ [adr/0004](adr/0004-delegate-retention-to-moneyforward.md)）。
- 「契約時の条件が曖昧にならないように」という要件は、この**受領資料の同一性担保**が本体。
  契約書PDFに添付する資料は、受領時のハッシュとファイル名・ページ数を契約書の別紙目録に印字する。

### 2.1 見積作成・送付

**現状（Phase 1）**: マネーフォワード クラウド請求書の画面で見積書を作成し、
本システムに見積書PDFと金額・見積番号を登録する。本システムから送信するメール本文に
契約用リンク（`/c/{token}`）を差し込み、見積書PDFを添付して送る。

**将来（Phase 4）**: MFクラウド請求書API v3 の `POST /quotes` で見積を作成し、
レスポンスの `pdf_url` を取得して添付する。
→ [docs/04-external-services.md](04-external-services.md)

**改正法対応**: 新設される法24条の10は「報酬の算定の根拠を明らかにするための見積書」の作成を
**努力義務**として定める。書面契約義務と違ってシステムで強制する対象ではない
（→ [01-legal-requirements.md §1.5](01-legal-requirements.md)）。
運用としては既定で作成し、見積の明細は業務報酬基準の算定根拠を保持できる構造とする
（一般は令和6年告示第8号、耐震診断・耐震改修は平成27年告示第670号）。
MF請求書の明細行（`items`）にマッピングできる粒度で持つ。
**見積が未作成でも契約フローはブロックしない**（警告のみ）。

なお法24条の10の対象は「**設計等の業務**に係る契約」であり、
書面契約義務が及ばない調査・耐震診断にも見積書の努力義務は及ぶ。

**リンクの仕様**

- URL: `https://<host>/c/{token}`
- `token` は 128bit 以上のランダム値（推測不可能）。DBにはハッシュのみ保存。
- 有効期限は見積の `expired_date` に合わせる（既定30日）。期限切れ時は再発行導線を出す。
- メール本文にもPDF内にも同じリンクを掲載する。PDFへの埋め込みは Phase 1 では手動、
  Phase 4 でPDF生成を内製化した際に自動化する。
- **リンク単体でアクセスできる情報は、その発注者・その案件に限定する。**
  リンク到達後に「メールアドレスの下4桁」等での追加確認を入れるかは UX と安全性のトレードオフ。
  MVPでは**リンク＋メールアドレス入力の照合**（送信先アドレスと一致することの確認）を必須とする。

### 2.2 ① 電磁的方法による交付の承諾

法令要件は [01-legal-requirements.md §4.1](01-legal-requirements.md) を参照。**この画面を飛ばせてはならない。**

画面に表示する内容:

- 電磁的方法の種類: 「当事務所のコンピュータに記録された書面記載事項を、電気通信回線を通じて
  お客様の閲覧に供し、お客様のコンピュータのファイルに記録する方法」（規則17条の39第1項1号ロ相当）
- ファイルへの記録の方式: 「PDF（PDF/A-2b）」
- 承諾しない場合・後から撤回する場合の連絡先と紙面交付への切替方法

保存するもの: 表示文言のスナップショット（バージョン管理）、承諾日時、IP、User-Agent、
承諾者が入力した氏名。

**撤回導線**: 契約締結前であればいつでも「電磁的方法による提供を受けない旨の申出」を送信できる
リンクをマイページと通知メールに常設する。撤回後は自動で紙面交付タスクを事務所側に起票する。

### 2.3 ② 重要事項説明書の閲覧・③ 説明の実施

> **このステップは相手方が建築主の場合のみ。**
> 法24条の7第1項は「設計受託契約又は工事監理受託契約を**建築主と**締結しようとするとき」と定めており、
> 元請け設計事務所からの受託など**相手方が建築主でない場合には適用がない**
> （→ [01-legal-requirements.md §3.0](01-legal-requirements.md)）。
> その場合は本ステップを丸ごとスキップし、① 承諾 → ④ 内容確認 へ進む。
> 書面の相互交付（22条の3の3）は建築主に限られないため、**契約書面の作成・締結は同じように行う**。

- 重説書面PDFを画面に表示し、ダウンロード可能にする（規則の「出力により書面を作成できること」）。
- **閲覧しただけでは説明義務を果たしていない。** 管理建築士等による説明と免許証の提示が必要。
- 画面には説明の予約導線（希望日時の入力）を置く。
- 事務所側の管理画面で、説明実施を記録する:
  実施日時 / 説明者（管理建築士等の氏名・資格区分・登録番号）/ 実施方法（対面・ビデオ通話）/
  免許証の提示方法 / 建築主の確認。
- 発注者側でも「説明を受けました」の確認操作を行い、双方の記録を突き合わせる。
- **適用がある契約で説明実施記録がない場合、締結ステップに進めない**（サーバ側ガード。UIだけで制御しない）。
  適用がない契約（相手方が建築主でない）でこのガードを効かせてはならない。締結を止める法的根拠がない。

### 2.4 ④ 契約内容の確認・追加入力

- 法定記載事項（[01-legal-requirements.md §2](01-legal-requirements.md)）を漏れなく埋めた契約書ドラフトを表示する。
- 発注者側で埋めるべき項目（正式な氏名・住所・連絡先、法人の場合は代表者名、建物の地名地番など）を
  この画面で入力させる。入力後に契約書PDFを再生成する。
- **受領図面等を契約書の別紙として添付する。** 添付目録には
  ファイル名 / ページ数 / 受領日 / SHA-256 を印字する。
- ドラフトの内容に相違がある場合の「修正を依頼する」導線を用意し、事務所側に差戻しを通知する。

### 2.5 ⑤ 決済

対象: 発注者が**一般消費者**の場合の前払金・手付金。法人取引は原則として締結後の請求書払い。

**推奨方式**: Stripe PaymentIntent を **manual capture（与信確保のみ）** で作成し、
締結完了後に capture する。

理由:
- 締結前に決済を確定させると、相手方が署名しなかった場合に返金処理が発生する。
- 与信確保であれば、締結不成立時は cancel するだけで済む。
- ただし**オーソリの有効期間はおおむね7日**であり、それを超えると再オーソリが必要。
  署名が7日以内に完了しない案件が一定数出るため、期限が近づいたら再オーソリを促す通知を実装する。

**代替方式**: 少額の手付金は即時決済（automatic capture）とし、締結不成立時は返金する。
どちらを採るかは金額帯で分岐させられるよう、契約種別ごとに設定可能とする。

**「MFのメール画面上で決済してもらう」ことについて**: できない。
マネーフォワード クラウド契約の署名画面は MF のドメインで提供され、
第三者が UI を差し込むことも遷移先を制御することもできない。
したがって**決済は自サイト内で完結させ、決済完了を署名依頼送信のトリガーとする**（上図の順序）。
順序を「締結後に決済」にしたい場合は、締結完了通知メール（自システムから送る）に
決済リンクを載せる形になり、未払いリスクが残る。
**消費者取引では「決済（与信）→ 署名依頼」の順を既定とする。**

### 2.6 ⑥ 署名依頼のトリガーと締結

発注者が「署名を依頼する」を押すと、クラウド契約 API v2 で次の順に実行する
（→ [04-external-services.md §1](04-external-services.md)、[adr/0002](adr/0002-esign-provider-abstraction.md)）。

> **⚠ 未検証。** v2 には有効なトークンでも到達できていない（403。→ 04-external-services.md §1.3）。
> 下記は仕様書に基づく想定であり、実挙動は Phase 0-1b で確認する。
> 到達できない間は `ManualMoneyForwardProvider`（事務所側の手作業）で運用する。
> **発注者から見た体験は変わらない。**

| # | 呼び出し | 内容 |
| --- | --- | --- |
| 1 | `POST /applications` | 申請を作成（事前にMF側でワークフローテンプレートの作成が必要） |
| 2 | `POST /applications/{id}/contracts` | 申請に紐づく契約を作成 |
| 3 | `PUT .../contracts/{cid}/document` | **契約書PDFをアップロード**。受領図面は別紙として契約書PDFに結合済み |
| 4 | `PUT .../contracts/{cid}/fields` | **契約情報を保存（必須）**。契約書名・契約開始日・終了日・契約金額の4項目は電帳法の要件を満たすために欠かせない |
| 5 | `PUT .../partner_companies`, `PUT .../partner_representatives` | 取引先企業と代表者（氏名・メール等）を登録 |
| 6 | `POST /applications/{id}/submit` | **提出**。ここでMFから署名依頼メールが飛ぶ |

- MFから発注者へ署名依頼メールが届き、MFの画面で署名する。
  v1 では承認者に**アクセスキー**（契約内容確認用の追加認証）をAPIから渡せたが、
  **v2 で同等の指定ができるかは未確認**（→ 04-external-services.md 未確定事項 #17）。
  渡せる場合は自システムで発行し、メールとは別経路で発注者に伝える。
- 事務所側も署名し、**相互交付**が成立する（法22条の3の3第1項）。
- 署名が滞っている場合は `POST /applications/{id}/remind` で催促する。
  決済のオーソリ期限（約7日）が近い案件を優先的にリマインドする。
- 締結完了は **Webhook で受信**する（`POST /webhooks` で登録）。
  v1 にはWebhookも締結状況の取得手段もなく、合意締結証明書の取得可否で判定する回避策が必要だったが、
  **v2 では `GET /contracts/{id}` で締結済み契約を直接取得できる**ため、この回避策は不要になる。
  Webhook の署名検証方式と配信イベント種別は Phase 0-1b で確認する。
- 締結完了後: `executed_at` と参照IDを記録、Stripe のオーソリを capture、
  発注者へ完了通知を送る。
  締結済契約書の永続保管をMF側に委ねるか自前でも退避するかは**再検討中**
  （v2 の `GET /contracts/{id}/document` で本体を取得できるため。→ [adr/0004](adr/0004-delegate-retention-to-moneyforward.md)）。
- 締結不成立・取下げ時は `POST /applications/{id}/withdraw` を呼び、
  Stripe のオーソリを cancel する。

> **`fields` は必須処理。ただし法定記載事項とは別物。**
>
> MFの案内では「契約書名・契約開始日・終了日・契約金額をすべて入力すると
> 電子帳簿保存法の『電子取引』の要件を満たすことが可能」とされている。
> 永続保管をMFに委ねる以上、**この4項目を送らないと保存要件を満たさない**。
> 送信前に4項目が揃っていることを検証し、欠けていたら `confirm` に進ませない（→ [03-architecture.md §6](03-architecture.md)）。
>
> 一方、**建築士法の法定記載事項が記載されるべき場所は契約書PDF本体**である。
> `fields` に入れたことをもって法定記載事項を満たしたことにはならない。
> 電帳法の要件と建築士法の要件は別物なので混同しないこと。

### 2.7 変更契約

法22条の3の3第2項により、法定記載事項に該当する内容の変更には変更書面の相互交付が必要。
同じフロー（承諾は取得済みなら再取得不要、重説は原契約時に実施済み）で
「変更契約」として ④〜⑥ を回す。契約は `version` を持ち、変更契約は親契約への参照を持つ。

## 3. ステータス遷移

```
DRAFT ─→ QUOTE_SENT ─→ CONSENT_GIVEN ─→ IMPORTANT_MATTERS_EXPLAINED
                              │            （重説の適用がある場合のみ経由）
                              │            └──────────┐
                              │(撤回)                  ↓
                              ↓                 TERMS_CONFIRMED
                        PAPER_FALLBACK                 │
                                                       ↓
                                                PAYMENT_AUTHORIZED（消費者取引のみ）
                                                       │
                                                       ↓
                                                SIGNATURE_REQUESTED
                                                       │
                                        ┌──────────────┼──────────────┐
                                        ↓              ↓              ↓
                                    EXECUTED       DECLINED       EXPIRED
                                        │
                                        ↓
                                  PAYMENT_CAPTURED
                                        │
                                        ↓
                                    COMPLETED
```

- 各遷移はサーバ側でのみ実行し、遷移条件を満たさない場合は 409 を返す。
- 遷移はすべて `contract_events` に追記のみで記録する（監査証跡。UPDATE/DELETE しない）。
